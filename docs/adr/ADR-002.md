# ADR-002. PostgreSQL, архив партии и квитанции команд

Версия: cp2-docs-draft, 24.11.2026. Статус: проект решения. Владелец: автор проекта (README).

Связи: US-003/005–011; NFR-003/006/009. Статус: предложено, серверная реализация не начата.

## Контекст

Подтверждённый ход не должен теряться; ответ может потеряться, а запрос прийти дважды. Текущий Core уже воспроизводит партию из раздачи и команд.

## Альтернативы

Файлы как в локальной игре: подходят одному устройству, но хуже для серверных гонок и доступа. Таблицы для каждой карты/слота: удобны для SQL-аналитики, однако плодят обновляемые представления состояния. Архив + реляционные метаданные сохраняет один источник истины.

## Решение

Один PostgreSQL 17. В matches хранить версию и внутренний архив JSONB: initialDeal, rulesVersion, имена и принятые игровые команды. initialDeal содержит исходный порядок колоды и первого игрока; сервер создаёт их криптографическим генератором. Комнаты, участники и квитанции команд — отдельные таблицы. Для хода: транзакция, блокировка строки партии, проверка квитанции, восстановление Core, действие, запись нового архива и точного ответа, COMMIT; только затем HTTP-успех.

## Последствия

Архив до 90 ходов можно воспроизвести целиком; стоимость надо измерить. Это не обещание event-sourcing инфраструктуры. Seed и архив никогда не выдаются клиенту. Квитанция хранит hash запроса; начальные ответы с токеном шифруются отдельным ключом. Изменение колоды/правил требует новой версии и миграции либо сохранения старого движка.

## Когда пересматривать

Пересмотреть при росте архивов, измеренном превышении задержек, необходимости аналитики по картам или несовместимых изменениях правил. Копирование БД каждые 15 минут проверяется отдельным восстановлением.
