## Границы

В локальной игре человек или TacticalBot отправляет PlayCardCommand в LocalMatchSession → GameEngine; MatchView обновляет экран; MatchSaveStore записывает файл. Текущий формат файла с резервной копией остаётся локальным. Он не используется как серверная БД и не доказывает транзакционные гарантии API.

Будущий API использует тот же Core, но создаёт PlayerId из проверенного участника. Переданный клиентом PlayerId не принимается. Внешний снимок содержит все руки своей партии, но только количество карт общей колоды. Seed, порядок колоды, hashes и токены других участников скрыты.

## Данные и ограничения D-05

- rooms: room_id PK, code UNIQUE (6 символов A–Z/2–9), host_member_id, status, version. Состав 2–4 при старте, 1–4 в ожидании. Изменения состава только в lobby.
- members: member_id PK, room_id FK, seat 0–3, name, token_hash UNIQUE. UNIQUE(room_id, seat), UNIQUE(room_id, member_id). Составная FK rooms(room_id, host_member_id) → members(room_id, member_id), отложенная до конца транзакции создания комнаты.
- matches: match_id PK, room_id FK UNIQUE, version >= 0, rules_version, archive JSONB, status. archive включает имена, initialDeal (исходный порядок карт и первый игрок) и принятые команды. Очки, карты и очередь восстанавливаются Core и не ведутся второй изменяемой копией.
- receipts: PRIMARY KEY(scope_key, command_id), request_hash, response_status, response_encrypted, created_at. Scope включает операцию и владельца: hash ключа первичного запроса либо room/match + member_id. Ответ зашифрован, потому что квитанция регистрации может содержать личный токен.
- migrations: номер и checksum применённой миграции. M001 создаёт таблицы/ограничения; код миграции ещё не написан. Демо-данные создаются через API, тестовые seed задаются только внутри тестового Core, не публичным клиентом.

Счётчик состава и ограничения переходов проверяются в транзакции под блокировкой комнаты. Карты, лимит 4 и версии проверяет Core. Одна партия блокируется на запись; разные партии независимы. Сначала блокируется ключ квитанции, затем агрегат — одинаковый порядок для всех изменяющих обработчиков. Уникальный ключ квитанции страхует гонку первого запроса; ответ проигравшего запроса берётся после завершения победившей транзакции.

## Версии, хранение и отказ

Версии комнаты и партии независимы. В комнате версия растёт при входе/старте; новая партия имеет version=0 после раздачи и начального добора. Каждый игровой ход повышает версию на 1. Повтор принятой команды проверяется до expectedVersion и возвращает сохранённый ответ. Изменённое тело с прежним ID даёт IdempotencyConflict.

На сервере надо добавить DTO архива и его проверку, транзакционный репозиторий, выдачу токенов и HTTP-сопоставление ошибок. Нынешняя Duplicate-ветка локальной сессии возвращает текущий View; для сети это недостаточно: точный старый HTTP-ответ хранится в receipts.

Локальная раздача использует 32-битный seed и xorshift для воспроизводимости, не для защиты от угадывания. На сервере запланированы CSPRNG-перемешивание и фабрика Core из явно заданной начальной колоды/первого игрока. Такой фабрики пока нет. Она меняет инициализацию и формат архива, но не правила хода. initialDeal хранится только внутри сервера; при восстановлении новая раздача не генерируется. Совместимость существующего локального seed-архива и нового серверного архива не предполагается; до реализации нужен отдельный тест воспроизводимости и отсутствия утечки порядка карт.

Неподтверждённый commit имеет неизвестный исход для клиента: он повторяет тот же commandId, а не создаёт новый. Если транзакция откатилась, повтор применит ход впервые; если сохранилась, вернётся квитанция. После повтора клиент делает GET и не заменяет новое поле старым снимком из квитанции.

Предложенное удержание данных: не начатая комната — 24 часа бездействия; партия, участники и квитанции — до 7 суток после завершения. Очистка согласованная, без переиспользования UUID. Во время открытой партии квитанции не удаляются.

## Стенд и ресурсы

Один учебный Linux-хост: 2 vCPU / 4 ГБ. Reverse proxy принимает HTTPS 443; API слушает 8080 только во внутренней сети; PostgreSQL 5432 наружу не опубликован. API ≤768 МиБ, БД ≤1024 МиБ, proxy ≤128 МиБ. NFR-011: API+БД вместе ≤2 ГБ под заданной нагрузкой.

Выбранные семейства: ASP.NET Core 10, PostgreSQL 17. Точные patch-версии SDK, NuGet-lock и digest образов фиксируются при создании каркаса; сейчас закреплённой сборки нет. Compose-файл и `.env.example` ещё не создавались. Секреты будущей среды: DB password и RECEIPT_KEY (AES-GCM), плюс TLS-ключ proxy. В Git значений быть не должно.

API: команда ≤16 КиБ, максимум 32 ожидающих записи на партию, пул БД 32 соединения, SQL timeout 2 с, server deadline 3 с. Переполнение очереди: 429 + Retry-After, недоступная БД: 503. /health проверяет процесс, /ready — связь с БД и версию схемы. Образы с healthcheck; именованный том БД; backup вне основного тома каждые 15 минут.

Метрики и методы остаются целями из NFR, не измеренными результатами. Порог 20 запросов/с из NFR-001 — базовая проверка, не доказательство максимальной нагрузки; фактический опрос всех клиентов дополнительно нагрузит сервис.

Механизм блокировок: [PostgreSQL 17](https://www.postgresql.org/docs/17/explicit-locking.html). Решения проекта изложены в ADR, а не заявлены как единственный возможный стек.
