# Проверки, исходные результаты и поставка

Версия: cp2-docs-draft, 24.11.2026. Статус: проект решения.


## Что действительно проверено

Отчёт локальной игры 0.2.0 от 23.11.2026: **22 проверки и 1080 полных партий** (900 случайных, 180 смешанных с тактическим ботом). C# Core и Storage компилировались Windows .NET Framework с предупреждениями как ошибками. Подтверждены раздача, ошибки без изменения состояния, повтор ID, стороны близнецов, оружие, сравнение, очки, ожидание, завершение, сохранение/восстановление и резервный файл.

Копия результата: [local-baseline.txt](local-baseline.txt). [baseline.json](baseline.json) фиксирует хеши файлов, версию и границы. Тесты не являются доказательством выполнения API, сети или SQL. При подготовке документов новый прогон не выполнялся.

Baseline покрытия строк/ветвей: **не измерен**. Число тестов и симуляций нельзя переводить в процент покрытия. После добавления .NET-проектов измерить Core отдельно и весь собственный серверный код; сохранить Cobertura/HTML и список исключений. К КТ-3: ≥80% правил и ≥70% всего прикладного кода. UI проверяется отдельно, но не скрывается из общего отчёта без обоснования границ метрики.

Unity-импорт, экранные проверки, Android APK, телефон, HTTP-интеграция, PostgreSQL, миграции, Docker и GitHub Actions не запускались в этой работе. Ссылки на успешный CI и серверное демо отсутствуют.

## Стратегия

1. Unit Core: существующие проверки перенести в серверный test runner, сохранить тестовые seed. Покрыть ошибки, полный порядок комбинаций, повторное оружие, ничьи и обязательность хода.
2. Integration: настоящая PostgreSQL в изолированном контейнере; миграции на пустую БД; репозиторий, квитанции, rollback, роли и токены. Проверить несовместимую версию архива и повреждённый JSON.
3. API: create → join → start → play → GET; негативный запрос не меняет состояние. Использовать токен текущего игрока, карту выбирать из его руки; не зашивать случайный CardId из примера.
4. Отказы: потеря ответа после COMMIT, остановка до COMMIT, недоступная БД и две одновременные команды. Для регистрации повторить первичный запрос с ключом восстановления; доказать, что посторонний по commandId токен не получает.
5. Приёмка: AT-001–011 по всем AC из stories; затем НФТ по методам PERF/RES/DUR/SEC/CON/OBS/QUAL/BACKUP/DEPLOY/RESOURCES/UI. У каждого прогона — SHA, дата, окружение, ожидаемый/фактический результат и ссылка на лог.

## План CI — обязательный на полной КТ-2

Запуск при PR и push в рабочую ветку. Установка SDK из global.json, пакетов с lock-файлом; эти файлы появятся вместе с кодом. Обязательные шаги: проверка OpenAPI; `dotnet format --verify-no-changes`; сборка с предупреждениями как ошибками; тесты; сборка Docker-образа; поиск секретов в изменениях и истории. Ошибка любого шага делает pipeline неуспешным. Для одиночного проекта — PR и self-review.

Сохранять test results, coverage, анализ и лог сборки на одном SHA. Провести два отрицательных эксперимента в отдельной ветке: намеренно сломанный тест и нарушение форматирования. Проверить красный CI, исправить, затем получить зелёный CI исходной версии. Сейчас этих запусков нет; workflow-файл намеренно не подменён пустой зелёной заглушкой.

К КТ-3 добавить coverage gate, интеграционные тесты контракта, SAST, аудит зависимостей и образа. Исключения фиксируются с причинами; тесты обязательных сценариев не скрываются skip/ignore.

## План CD и отката

Цель: отдельная учебная Linux VM, 2 vCPU/4 ГБ. После зелёного CI релизный job собирает и публикует образ с SHA и digest в registry. Deploy job с возможным ручным подтверждением получает именно этот образ, запускает совместимую миграцию, readiness и smoke-сценарий создания/хода. Ручное копирование исходников на сервер не считается CD.

При ошибке: статус deploy failed, возврат предыдущего digest, readiness и smoke. Миграции сначала только добавляющие и совместимые с предыдущей версией; разрушающие изменения — отдельный этап после окна отката. Если схема несовместима, восстановление БД из проверенной копии с явно указанным интервалом потери. Backup вне тома БД каждые 15 минут; цель RPO ≤15 минут, RTO ≤5 минут при БД до 100 МБ.

Недоверенные PR не получают секретов deploy. Пароль БД, ключ шифрования квитанций и TLS-ключи передаются настройками среды. Команды запуска/остановки и миграции нельзя считать готовыми до появления compose и проверки чистого checkout. Точный стенд, образы, секрет-хранилище и ссылка на журнал будут заполнены при реализации.
